# 2D

Bevy 0.20's 2D in TSX: a `Camera2d`, flat meshes and their `ColorMaterial`, sprites, and picking.
Rust components keep their Rust field names (`<Sprite custom_size>`); intrinsics take camelCase
props, as `<mesh>` does. `examples/shapes-2d` shows each working row; 2D does not show in the
editor's 3D view, so run it with `bevy-ts dev src/game.tsx` from that folder, or switch the
editor's viewport to the game view (`viewport_mode { camera: "game" }`, [viewport](viewport.md)).

```tsx
<>
  <entity><Camera2d /></entity>
  <entity>
    <Transform translation={[-150, 0, 0]} />
    <mesh2d shape="circle" radius={50} />
    <material2d color="#f80" alpha={0.8} />
  </entity>
  <entity>
    <Sprite image="hero.png" flip_x />
  </entity>
</>
```

## Pixel art

Set `"imageSampler": "nearest"` in `bevy-ts.json`, so every sprite samples its texels whole
instead of blurring them ([assets](assets.md#the-projects-default-sampler)). An image given its own
sampler keeps it.

## `<mesh2d>` and `<material2d>`

`<mesh2d shape>` builds a `Mesh2d` from one of `<mesh>`'s 2D shapes (`circle`, `circularSector`,
`circularSegment`, `ellipse`, `annulus`, `rectangle`, `rhombus`, `regularPolygon`, `triangle2d`,
`capsule2d`, `convexPolygon`), with the same props and checks ([meshes.md](meshes.md)). It is flat
in the XY plane facing +Z, so it takes no `depth` or `segments`. Equal props share one mesh asset,
also with a `<mesh>` of the same shape. `color` is a shorthand for `<material2d color>`.

`<material2d>` is a `ColorMaterial`:

| prop | Bevy | |
|---|---|---|
| `color` | `color` | any colour form; default white |
| `alpha` | the colour's alpha | 0 to 1 |
| `alphaMode` | `alpha_mode: AlphaMode2d` | `"opaque"`, `"blend"` or `{ mask: n }`; unset, `"blend"` below alpha 1, else `"opaque"` |
| `texture` | `texture` | an asset path |
| `uvTransform` | `uv_transform` | `{ scale?, rotation?, translation? }`, as on `<material>` |

Equal props share one material. Props cannot be bindings. `<material2d kind={Planet} />` is
instead a script 2D material, its WGSL and params declared in TS with `material2d()`: see
[materials.md, 2D materials](materials.md#2d-materials). Bevy keeps 2D and 3D apart, so
`<mesh2d>` pairs with `<material2d>` and `<mesh>` with `<material>`: mixing them on one entity
fails the load at the element. The code is `crates/bevy-ts-tsx/src/intrinsics.rs`; the types are
`Mesh2dProps` and `Material2dProps` in `bevy-ts/jsx-runtime`.

## Sprites

`Sprite` is Bevy's component, so its props are its Rust fields in Bevy's reflected form:

| prop | TS |
|---|---|
| `image` | an asset path |
| `color` | any colour form |
| `flip_x`, `flip_y` | booleans |
| `custom_size` | `[w, h]` |
| `rect` | `{ min: [x, y], max: [x, y] }`, a region of the image in pixels |
| `image_mode` | `"Auto"`, `{ Scale: "FitCenter" }`, `{ Sliced: { border: { min_inset, max_inset }, center_scale_mode, sides_scale_mode, max_corner_scale } }`, `{ Tiled: { tile_x, tile_y, stretch_value } }`, or UI's `sliced({ border: 8 })` and `tiled(...)`, which return those |
| `alpha_mode` | `"Opaque"`, `"Blend"` or `{ Mask: n }` |

`<Anchor value={[-0.5, 0.5]} />` moves the sprite's origin to its top left. A sprite takes pointer
events on its entity through Bevy's sprite picking; a `<mesh2d>` takes them once `meshPicking` is
on in `bevy-ts.json`.

## Atlases

A sprite sheet is a grid layout and a tile:

```tsx
import { Sprite, TextureAtlasLayout } from "bevy-ts/bevy";

const sheet = TextureAtlasLayout.fromGrid({ tileSize: [32, 32], columns: 4, rows: 1 });

<Sprite image="sheet.png" texture_atlas={{ layout: sheet, index: 2 }} />
```

`fromGrid` is Bevy's `TextureAtlasLayout::from_grid` (`tileSize`, `columns`, `rows`, and
`padding` and `offset`, in whole pixels). It is an asset value, so every slot given an equal grid
shares one layout, `<image atlas={{ layout: sheet, index }}>` too. An `index` past the grid's
tiles fails the load, naming both.

`<SpriteClip>` animates a sheet, as Bevy's `sprite_animation` example's timer does:

```tsx
import { Sprite, SpriteClip, TextureAtlasLayout } from "bevy-ts/bevy";

<entity>
  <Sprite image="walk.png" texture_atlas={{ layout: sheet, index: 0 }} />
  <SpriteClip first={0} last={3} fps={10} mode="Repeat" />
</entity>
```

- It steps `texture_atlas.index` from `first` to `last` at `fps` frames a second of virtual time,
  so a paused game holds the frame. `mode` is `"Repeat"`, `"Once"` (holds `last`, then sets
  `finished` once `last` has shown its full time) or `"PingPong"` (first to last and back).
- `playing={false}` holds the frame. A change of `first`, `last` or `mode` starts again at
  `first`, so one clip component switches a character from walking to idling.
- `last` below `first`, `fps` not above 0, a sprite with no `texture_atlas`, or a `last` past the
  layout's tiles logs one error naming the field (and the index and count), and the frame stays.
- The frames are one contiguous run of the sheet; a list of frames is not supported.

By hand, a TS system animates a sheet as Bevy's `sprite_sheet` example does: a timer on the
sprite, and the next tile when it finishes.

```tsx
export class Frames extends Component {
  timer = Timer.fromSeconds(0.1, "Repeating");
  last: u32 = 3;
}

export function animate(time: Res<Time>, sheets: Query<[Mut<Sprite>, Mut<Frames>]>) {
  for (const [sprite, frames] of sheets) {
    if (!frames.timer.tick(time.delta_secs).just_finished) continue;
    const atlas = sprite.texture_atlas;
    if (!atlas) continue;
    atlas.index = atlas.index === frames.last ? 0 : atlas.index + 1;
  }
}
app.addSystems(FixedUpdate, animate);
```

`sprite.texture_atlas` is a copy; changing it on a `Mut` row writes it back at the end of the run
([native](native.md#reflected-rows-in-ts-systems)). Its `index` reads as a number, and takes a number
or a string.

## Y-sort

`<YSort />` draws an entity by its base y within a layer: lower on screen is in front, as
characters walk past trees and each other.

```tsx
import { Sprite, YSort } from "bevy-ts/bevy";

<entity>
  <Transform translation={[x, y, 0]} />
  <Sprite image="hero.png" />
  <YSort layer={1} offset={-8} />
  <entity>
    <Transform translation={[0, -8, -0.00001]} />
    <Sprite image="shadow.png" />
  </entity>
</entity>
```

It sets the entity's `Transform` z, before Bevy propagates transforms, to

    z = layer - clamp(y + offset, -49999, 49999) × 0.00001

- `y` is the entity's own `Transform` y: its world y at the root, its y in its parent's space under
  a parent (its z then adds to the parent's, so it sorts among its siblings). Y-sort is meant for
  roots and for siblings under one still parent.
- `offset` moves the base from the origin to the feet: `-8` for a 16 px sprite centred on its
  origin.
- `layer` is the whole layer it draws in, from -127 to 127: ground at 0, characters and trees at
  1, roofs at 2. Layers never mix. A layer past 127 logs an error naming `YSort.layer` and the
  value, and leaves z alone.
- Past ±49,999 px of base y, sprites tie and draw in no set order; the first time an entity goes
  there, a warning names it.
- A child without `YSort` keeps its own z, added to its parent's: one pixel of y is 0.00001, so a
  shadow at local z -0.00001 draws behind its character and in front of what stands two pixels or
  more further up.
- `YSort` owns `Transform` z: a script's write to z is overwritten the same frame, so write
  `layer`. A level saved from the world holds the derived z beside `YSort`, and loading it
  recomputes z on the first frame: the saved z decides nothing.
- `GlobalTransform` is Bevy's own propagation of the `Transform`, so picking and every other reader
  see what is drawn. A bound y has its new z the same frame. Bevy 0.20 keeps a 2D mesh's draw
  order from the z it was queued at, so while a `YSort` exists, a sprite or 2D mesh whose global z
  moves is queued again (its `Mesh2d` is marked changed): it draws in its new place that frame or
  the next, and a y-sorted character's shadow child follows it. A still entity's `Transform` is
  not written again, so it costs a read and a compare; with no `YSort` in the world the pass does
  not run.
- A Rust app adds `bevy_ts_material::Pixel2dPlugin` beside `DefaultPlugins`; the pass is
  `Pixel2dSystems`, in `PostUpdate` before `TransformSystems::Propagate`.

## Pixel camera

`<PixelCamera zoom={2} />` on a `Camera2d` zooms by whole numbers, so every texel covers whole
screen pixels, as Stardew draws at the window's resolution.

```tsx
<entity>
  <Camera2d />
  <PixelCamera zoom={2} ease={0.25} />
  <Transform translation={[x, y, 0]} />
</entity>
```

- `zoom` is screen pixels per texel, a whole number from 1: the orthographic projection's `scale`
  is `1 / zoom` (Bevy's `ScalingMode::WindowSize`, so on a 2x display a texel is `2 × zoom`
  physical pixels). A zoom that is not whole logs an error naming `PixelCamera.zoom` and the value,
  and the scale stays.
- A change of `zoom` eases the scale there over `ease` seconds (default 0.25) with a cubic
  ease-out, about the camera's centre, on real time, so a paused game still zooms. `ease={0}`
  jumps. Mid-ease the zoom is not whole for those frames.
- `PixelCamera` owns the projection's `scale`: a script's write is overwritten, and a level saved
  from the world holds the derived scale. Write `zoom`. It also turns the camera's `Msaa` off,
  which multisampling would otherwise blend a sub-pixel sprite's edge pixels with.
- The view is drawn from the camera's position rounded to whole screen pixels (half a pixel more
  on an axis whose size in pixels is odd), by a shift of the projection's `viewport_origin`. The
  camera's `Transform` and `GlobalTransform` keep the script's values, and picking builds its ray
  from the same projection, so a click hits what is drawn.
- Sprites are not snapped one by one: at a whole zoom with nearest sampling
  ([pixel art](#pixel-art)), a sprite at any sub-pixel position covers the same whole pixels as
  at its nearest pixel. A sprite moving at exactly half-pixel steps may flicker by one pixel.
- One `PixelCamera` rules, the first added; a second logs one warning naming both and zooms
  nothing.

## Screen-size sprites

`<ScreenSize />` keeps a sprite one size on screen at every zoom: a marker over a building reads
the same at 1x and 4x, while it stays in the world, y-sorted and pickable.

```tsx
<entity>
  <Transform translation={[120, 64, 0]} />
  <Sprite image="marker.png" />
  <ScreenSize />
</entity>
```

- It sets `Transform` scale x and y to `scale` (default 1) times the ruling camera's orthographic
  scale, before Bevy propagates transforms: at `Projection` scale 0.25 (zoom 4) a marker's scale is
  0.25, so each image pixel is one screen pixel. `scale={2}` makes each two.
- The ruling camera is the `PixelCamera`'s, else the first `Camera2d` by `Camera.order`, then by
  entity. With none, nothing is written. A pixel camera's scale is written first in the pass, so a
  marker follows a zoom the same frame, easing included.
- Its children scale with it, about its origin. Under a scaled parent the parent's scale multiplies
  in.
- `ScreenSize` owns `Transform` scale x and y, as `YSort` owns z: a script's write is overwritten
  the same frame, so write `scale`. z scale stays the entity's own.
- Sprite picking reads Bevy's `GlobalTransform`, so a click hits the drawn size.

## Text

`<text2d>` is Bevy's `Text2d` on its entity, placed by the entity's `Transform` in pixels:

```tsx
<entity>
  <Transform translation={[0, 40, 0]} />
  <text2d size={24} color="#fff" anchor={[0, -0.5]}>
    Score {() => score()}<span color="#f44">!</span>
  </text2d>
</entity>
```

It takes `<text>`'s props (`size`, `color`, `font`, `weight`, `italic`, `justify`, `linebreak`,
`lineHeight`, `letterSpacing`, `textBackground`, `underline`, `strikethrough`, and `textShadow`,
which writes `Text2dShadow` with y up), and its children the same way: strings, bindings and
`<span>`s, each `<span>` a child entity. It adds `anchor` (`Anchor`: a side, a corner or `[x, y]`
from -0.5 to 0.5) and `bounds` (`TextBounds`: `[width, height]` in pixels, either `null`). Props
and children bind, and a change writes only its component. It is no UI node, so it takes no
`style`.

## Bitmap text

`<bitmapText>` draws text in a bitmap font: an XNA `SpriteFont` exported as JSON beside its PNG
(StardewXnbHack writes Stardew's this way), laid out as MonoGame lays it out.

```tsx
<entity>
  <Transform translation={[0, 120, 0]} />
  <bitmapText font="stardew://Fonts/SmallFont.json" color="#fff" scale={1} anchor="top-left">
    Day {() => day()}
  </bitmapText>
</entity>
```

- `font` is the JSON's asset path. It loads as a `SpriteFont` asset: `texture.export` (the PNG,
  beside the JSON, in the same source, sampled nearest), `glyphs`, `cropping`, `characterMap`,
  `verticalLineSpacing`, `horizontalSpacing`, `kerning` (each glyph's left bearing, width and right
  bearing) and `defaultCharacter`. Lists of unequal length fail the load naming the field and both
  counts; a missing PNG fails it naming the path.
- Its children are strings, numbers and bindings, joined. A changed binding lays the glyphs out
  again the same frame.
- `color` tints every glyph (white by default), `scale` multiplies every position and size (1 by
  default), and `anchor` places the measured box as `<text2d>`'s does (`"center"` by default), its
  point of the box rounded down to a whole pixel so an odd-sized box stays on whole pixels.
- The layout is MonoGame's (`SpriteFont.cs` `MeasureString`, `SpriteBatch.cs` `DrawString`): a
  line's first glyph starts at its left bearing if positive, each next one after the spacing and
  its left bearing, each draws at its cropping offset, `\n` starts a line `verticalLineSpacing`
  lower. A character the font lacks draws `defaultCharacter`, or is skipped with one warning
  naming it when the font has none. Positions are whole pixels times `scale`. No wrapping.
- Each glyph is a child entity with a `Sprite` cut from the font's PNG by `rect`, so a label is one
  batched draw. The glyphs are bitmap text's own: the reconciler keeps them, levels never write
  them, and they go with the element. They move with the entity's `YSort` and scale with its
  `ScreenSize`.
- The studio's asset list shows the font loader for every `.json`: Bevy picks it by the asset
  type a load asks for, so other JSON loads are untouched.
- A Rust app adds `bevy_ts_material::BitmapTextPlugin` and inserts `BitmapText { text, font,
  color, scale }`.
## Tilemaps

A `TilemapChunk` draws a grid of tiles as one mesh, its tiles in `TilemapChunkTileData`, one per
cell from the bottom-left, row by row (`null` is an empty cell):

```tsx
import { Image, TilemapChunk, TilemapChunkTileData } from "bevy-ts/bevy";

const tileset = Image.load("tiles.png", { array_layout: { RowCount: { rows: 4 } } });

<entity>
  <TilemapChunk chunk_size={[4, 4]} tile_display_size={[32, 32]} tileset={tileset} />
  <TilemapChunkTileData value={tiles.map((i) => (i < 0 ? null : { tileset_index: i }))} />
</entity>
```

- `tileset` is an array texture, one layer per tile: `Image.load` with Bevy's `array_layout`
  (`{ RowCount: { rows } }` for tiles stacked in a column, or `RowHeight`, `GridCount`,
  `GridSize`), or an image ref. A bare path, or `Image.load` with no `array_layout`, fails the
  load naming the fix.
- A tile is `{ tileset_index, color?, visible?, orientation? }`, its unset fields Bevy's
  `TileData` default. The array is `chunk_size.x * chunk_size.y` long; any other length fails
  the load naming both.
- `tile_display_size` is the tile's size on screen in pixels, not in the image.
- `TilemapChunk` is immutable in Bevy: a changed prop inserts it again, and Bevy builds the
  chunk's mesh anew. Changed tile data is written in place, and Bevy updates the chunk.

## Fullscreen passes

`<pass kind={Dusk} amount={() => dark()} />` on a `Camera2d` grades its whole image with a WGSL
fragment declared in TS, after tonemapping: dusk, fog. It keeps pixel art crisp. See
[materials.md, Fullscreen passes](materials.md#fullscreen-passes).
