# remote-protocol Specification

## Purpose
The `bevy-ts/*` methods served on stock `bevy_remote`, through which editors, the inspector and tools read and change a running bevy-ts engine, and the versioned OpenRPC document that types them.

## Requirements

### Requirement: Served on top of stock bevy_remote
bevy-ts SHALL add its methods to Bevy 0.20's `RemotePlugin` with `with_method_main` and `with_watching_method_main`, over `RemoteHttpPlugin` (default 127.0.0.1:15702; watching methods stream as server-sent events). Every stock method (`world.*`, `registry.schema`, `schedule.*`, `rpc.discover`) SHALL stay available and unchanged. All bevy-ts methods SHALL be named `bevy-ts/<name>`, with the `+watch` suffix for streaming ones. The protocol SHALL be on under `bevy-ts dev` and off in release builds unless enabled.

#### Scenario: Stock and bevy-ts side by side
- **WHEN** a client calls `world.list_components` and then `bevy-ts/hello` on the same port
- **THEN** both answer, the first exactly as stock `bevy_remote` does

### Requirement: One versioned schema file is the contract
The protocol SHALL be defined by `protocol/bevy-ts.openrpc.json`, an OpenRPC 1.3.2 document (the version `rpc.discover` emits) whose `info.version` is the protocol's semver and whose params and results are JSON Schema. bevy-ts's Rust types SHALL be generated from it, and the npm package SHALL export TS types generated from it at `bevy-ts/protocol`. Generation SHALL be deterministic, and CI SHALL fail when regenerated output differs from what is checked in. A field or method added is a minor bump; anything removed, renamed or retyped is a major bump.

The file SHALL also hold methods owned by other bevy-ts crates. They follow the same `bevy-ts/<name>` naming and versioning rules and are generated by the same pipeline, and each method records its owning crate in an `x-bevy-ts-crate` field. A feature crate's methods SHALL be served only when that crate's plugin is added.

#### Scenario: A feature crate adds a method
- **WHEN** a feature crate adds `bevy-ts/example_method` to the file
- **THEN** its Rust and TS types come out of the same codegen run, the protocol takes a minor bump, and a game without that crate's plugin answers it with method-not-found

#### Scenario: Drift between file and code
- **WHEN** someone edits a generated Rust type by hand
- **THEN** CI regenerates from the schema file and fails on the diff

### Requirement: Handshake
`bevy-ts/hello` SHALL return the protocol version, the bevy-ts, Bevy and JS engine versions, the entry file, the current generation and whether dev features (reload, inspector) are on. `bevy-ts/discover` SHALL return the OpenRPC document the server was built with.

#### Scenario: A studio built for an older major
- **WHEN** the studio supports protocol 1.x and `bevy-ts/hello` returns `2.0.0`
- **THEN** the studio can tell from the handshake alone and refuse to attach

### Requirement: Reload over the protocol
`bevy-ts/reload` (params `restart?: boolean`) SHALL recompile from disk and answer with the resulting generation, `applied` or `failed`, errors with TS locations, and migrations performed. `bevy-ts/reload+watch` SHALL stream one message per reload attempt from any cause (save, request), with `compiling`, then `applied` or `failed`, and the duration. Outside dev mode `bevy-ts/reload` SHALL return a method error.

#### Scenario: A studio triggers a reload
- **WHEN** the studio calls `bevy-ts/reload` after the user saves elsewhere
- **THEN** it gets the new generation number and the game runs it from the next frame

### Requirement: Component schemas, TS components included
`bevy-ts/schema` SHALL return one schema per component known to the world: every TS component (live and undeclared) and every reflected Rust component, in the same JSON Schema shape stock `registry.schema` uses (`typePath`, `shortPath`, `kind`, `properties`, `reflectTypes`, `componentInfo`). TS components SHALL add an `x-bevy-ts` object: `source: "ts"`, file and line of the declaration, `declared`, the layout (size, align, field offsets and types), and per-field editor hints and defaults. Params MAY filter by name or by `source`.

#### Scenario: One renderer for both kinds
- **WHEN** the studio's inspector asks for `game::Mover` and `bevy_transform::components::transform::Transform`
- **THEN** both come back as `kind: "Struct"` schemas with `properties`, and only `game::Mover` has `x-bevy-ts`

### Requirement: Reading components, TS components included
`bevy-ts/get_components` SHALL take the params of stock `world.get_components` (`entity`, `components`, `strict`) and return the same shape, serving TS components from their native layout and delegating reflected ones to reflection. `bevy-ts/get_components+watch` SHALL stream like stock `world.get_components+watch`, including TS components, sending only components whose change tick moved since the last message.

#### Scenario: Inspecting the cube
- **WHEN** the inspector calls `bevy-ts/get_components` for the cube with `game::Mover` and `Transform`
- **THEN** the result has both, `game::Mover` as `{ "speed": 1.0, "amplitude": 2.0 }`

### Requirement: Editing a field
`bevy-ts/mutate_components` SHALL take stock `world.mutate_components`'s params (`entity`, `component`, `path`, `value`) for any component. For TS components, `path` SHALL accept `.field`, `.field.x|y|z|w` for vectors and `.field[i]` for arrays; the value SHALL be checked against the field type and hints, written into the column, and the change tick set so watchers and `Changed` see it. An invalid path or value SHALL return an error naming the path and the expected type, and write nothing.

#### Scenario: Dragging a number in the inspector
- **WHEN** the inspector sends `{ entity, component: "game::Mover", path: ".amplitude", value: 4 }`
- **THEN** the cube's bob widens on the next frame, and the next `bevy-ts/get_components+watch` message carries `amplitude: 4`

#### Scenario: A wrong type
- **WHEN** the value for `.amplitude` is `"wide"`
- **THEN** the call fails with an error saying `.amplitude` expects `f32`, and the component is unchanged

### Requirement: Pausing for editing
`bevy-ts/pause` (`paused: boolean`) SHALL stop or resume all bevy-ts stages and `Time<Virtual>`, so an edited value is not overwritten by a system on the next frame. `bevy-ts/step` (`frames: number`, default 1) SHALL, while paused, run that many frames and pause again. The window and rendering SHALL keep running while paused. Before the game has started (see edit-mode), `bevy-ts/pause` with `paused: false` SHALL fail with "the game has not started; switch to play", and leave it paused.

#### Scenario: Editing a paused game
- **WHEN** the game is paused and the inspector sets the cube's `translation.y` to 3
- **THEN** the cube stays at 3 until the game resumes

#### Scenario: Stepping one frame while paused
- **WHEN** the game is paused and the client calls `bevy-ts/step` with `frames: 1`
- **THEN** every stage and `Time<Virtual>` advance by exactly one frame, and the game is paused again

#### Scenario: Resuming a game that never started
- **WHEN** an `--edit` engine has not played and a client calls `bevy-ts/pause` with `paused: false`
- **THEN** the call fails with "the game has not started; switch to play" and no TS system runs

### Requirement: Entity and scene change events
`bevy-ts/entities` SHALL return a snapshot of every entity but bookkeeping (observers, resource entities, `ScriptHidden` entities, and the engine's windows and picking pointers): each entity's id, `Name` if any, parent, and the names of all its components (TS and Rust). `bevy-ts/entities+watch` SHALL first send that snapshot with a sequence number, then at most one message per frame with what changed that frame: spawned (with the snapshot fields), despawned, reparented, renamed, components added and components removed. Each message SHALL carry the next sequence number; a client that sees a gap SHALL resubscribe. Field values are not part of this stream.

#### Scenario: Spawning from TS shows in the scene tree
- **WHEN** a TS system spawns an entity named `bullet` as a child of the cube
- **THEN** the next message lists it under `spawned` with its parent and components, in the same frame's message

#### Scenario: A quiet frame
- **WHEN** nothing structural changes in a frame
- **THEN** no message is sent for that frame

#### Scenario: The engine's own entities after a Stop
- **WHEN** a viewport engine stops a played game and a client calls `bevy-ts/entities`
- **THEN** neither the virtual window's entity nor any `PointerId` entity is listed, nor in the `bevy-ts/entities+watch` snapshot

### Requirement: Systems and logs
`bevy-ts/systems` SHALL list TS systems with name, stage, read, write, generation, last run time in microseconds and last error. `bevy-ts/log+watch` SHALL stream `console.*` output and bevy-ts errors and warnings with level, TS location and generation.

#### Scenario: A throwing system shows in the studio
- **WHEN** `bob` throws
- **THEN** `bevy-ts/log+watch` streams the error with `game.ts` line and `bevy-ts/systems` shows it as `bob`'s last error

### Requirement: Schemas say whose a component is and how an editor treats it
Every entry `bevy-ts/schema` returns, TS and Rust alike, SHALL carry an `x-bevy-ts-editor` object with four fields, all required:

- `origin`: `"engine"` when the component's type comes from one of Bevy's own crates at the pinned Bevy version or from a bevy-ts crate; `"game"` for every TS component and for a type from the project's native crate; `"plugin"` for a type from any other crate. Origin SHALL be decided from the type's crate, not from a name prefix: `bevy_rapier3d` is `plugin`.
- `internal`: `true` for a component the engine maintains and nobody authors (GlobalTransform, InheritedVisibility, ViewVisibility, VisibilityClass, Aabb, TransformTreeChanged, TransformGizmoFocus, Children and the like). bevy-ts SHALL own this list. Only an `engine` component SHALL ever be internal.
- `addable`: `true` when an editor may offer the component in Add component: a reflected Component with `ReflectDefault` or `ReflectFromWorld`, mutable, not a resource (Bevy 0.20 stores resources as components; they carry `ReflectResource`) and not internal; a TS component while its live generation declares it. Otherwise `false`.
- `category`: one of `transform`, `render`, `light`, `camera`, `physics`, `audio`, `ui`, `animation`, `game`, `other`. Every `game` component SHALL be `game`. An `engine` component SHALL take its category from bevy-ts's table, `other` when unlisted. A `plugin` component SHALL be `other` unless bevy-ts's table names its crate.

`bevy-ts/schema` without `names` SHALL still list every registered reflected Component and every TS component, live and undeclared. `x-bevy-ts` SHALL stay as it is, present on TS components only. A client SHALL treat an unknown `category` as `other`, and an entry without `x-bevy-ts-editor` as from an engine before protocol 1.11.0.

#### Scenario: The inspector hides what the engine maintains
- **WHEN** the inspector asks `bevy-ts/schema` for `bevy_transform::components::global_transform::GlobalTransform` and `bevy_transform::components::transform::Transform`
- **THEN** both have `origin: "engine"` and `category: "transform"`, GlobalTransform has `internal: true` and `addable: false`, and Transform has `internal: false` and `addable: true`

#### Scenario: A resource is never offered for an entity
- **WHEN** the inspector asks `bevy-ts/schema` for `bevy_camera::clear_color::ClearColor`
- **THEN** its entry has `addable: false`

#### Scenario: A TS component is the game's
- **WHEN** the live generation declares `game::Mover`
- **THEN** its entry has `x-bevy-ts-editor` `{ origin: "game", internal: false, addable: true, category: "game" }` beside its `x-bevy-ts`

#### Scenario: An undeclared TS component cannot be added
- **WHEN** a reload drops `game::Mover` but entities still hold its data
- **THEN** its entry has `addable: false` and `x-bevy-ts.declared: false`

#### Scenario: A third-party crate is a plugin
- **WHEN** the rapier example's engine answers `bevy-ts/schema` for `bevy_rapier3d::dynamics::rigid_body::RigidBody`
- **THEN** its origin is `plugin`, not `engine`, and its category is `physics` because bevy-ts's table names `bevy_rapier3d`

#### Scenario: The project's native crate is the game's
- **WHEN** a project's native crate `native` registers a reflected component `native::Fuel`
- **THEN** its entry has `origin: "game"` and `category: "game"`

### Requirement: Each subscriber of a watch is served on its own
Every `+watch` method SHALL serve each open request on its own, even when several have the same params: each SHALL get the method's opening message when it opens, then every message owed to it after. A request that was not served for an update SHALL count as closed, so the same params opened again get the opening message again. When a request closes, another with the same params SHALL NOT miss a message, and `bevy-ts/level+watch`, which sends one event per update, MAY send one again; a request that opens in the update another with the same params closes MAY get no opening message. A Stop SHALL NOT restart open watches.

#### Scenario: A second studio window opens the same watch
- **WHEN** a client has `bevy-ts/viewport_tools+watch` open and a second request with the same params opens later
- **THEN** the second is sent the tools on open, and on the next change both are sent it

#### Scenario: A second window opens the asset watch as a file lands
- **WHEN** a client has `bevy-ts/assets+watch` open, a file is added, and a second request with the same params opens before the first is sent the change
- **THEN** the second's list has the file, and the first is still sent it as `added`
