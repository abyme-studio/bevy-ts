## Context

`<material color>` builds a `StandardMaterial` in `bevy-ts-tsx/src/intrinsics.rs`, cached by props in `IntrinsicAssets`, so equal props share one handle: every red cube holds the same asset. `insert_material` inserts `MeshMaterial3d(handle)` on the entity, again on each reconcile; `remove_material` removes it. `StandardMaterial::default()` is `Opaque`, which ignores alpha. `<material>` props cannot be bindings (`resolve.rs` refuses them); component fields can, and a binding writes the field each frame.

A glTF scene root is an entity with `WorldAssetRoot`. Its meshes are the instance's own entities, each with a `MeshMaterial3d<StandardMaterial>` whose handle is the glTF's labelled material, shared by every instance of that model. `scene-material` (lands first, same crate) walks them: `scene_entities(world, root)` returns the instance's entities, empty until ready, and it re-runs on `WorldInstanceReady`. It swaps matching meshes to a `ScriptMaterial3d` and keeps their originals in `SceneMaterialTargets` on the root.

## Decisions

1. **Names follow Bevy: `alpha`, `alphaMode`, `MaterialAlpha`.** Bevy calls it alpha everywhere (`Color::alpha`, `with_alpha`, `AlphaMode`); "opacity" appears on no Bevy material. `alphaMode` reuses `kinds::AlphaDecl` and its parser and the `AlphaMode` TS type from `bevy-ts/material`, so one parser owns the names. The component is `MaterialAlpha`, not `SceneAlpha`: it fades a plain mesh as well as a scene, and Bevy names a component after what it holds (`Visibility`, `NotShadowCaster`), not the kind of entity it sits on.
2. **The default mode is Bevy's own rule.** `StandardMaterial::from(Color)` picks `Blend` below alpha 1 and `Opaque` otherwise. `<material>` does the same on its final alpha, so `alpha={0.5}` alone is see-through. `StandardMaterial::default()` stays `Opaque` in Bevy because it has no colour yet; we always have one. An author who wants a cutout says `alphaMode={{ mask: 0.5 }}`. Side effect: an existing `color="#rrggbbaa"` with alpha below 1 now blends, which is what it asked for.
3. **The fade is a component, not a `<material>` prop.** A bound `<material alpha>` would make one cached asset per distinct value, and a root has no material of its own. `MaterialAlpha` is a layout-tier component (`#[derive(Component, Reflect, Default)]`, one `f32` field), so it is bindable with no new binding path, writable from TS systems, and usable from Rust. `alpha` is clamped, not refused, because a binding writes it every frame. `<material alpha>` stays: it is a shape's resting look, and `MaterialAlpha` multiplies it.
4. **What it fades.** An entity's targets are: the entity itself, if it holds a `MeshMaterial3d<StandardMaterial>`; and, if it has `WorldAssetRoot`, every entity `scene_entities` returns that holds one. TSX children are not targets; a child takes its own `MaterialAlpha`. Inheriting through the hierarchy is a follow-up, as Bevy's own `Visibility` inheritance is separate from materials.
5. **One copy per distinct original per entity, edited in place.** The originals are shared (by every red cube, by every instance of a model), so fading them would fade them all. On first sync the entity clones each distinct original its targets hold and points those targets at the copy. `MaterialAlphaTargets` on the entity keeps `target -> original` and `original -> copy`. A changed `MaterialAlpha` (`Changed<MaterialAlpha>`) rewrites only the copies' `base_color` alpha and `alpha_mode`, skipping a copy whose values are already right. No asset is added or dropped while the fade runs. Removal points each target still holding a copy back at its original and drops `MaterialAlphaTargets`, which frees the copies.
6. **A target's material changes under it.** A TS save re-runs `insert_material`, which inserts a handle on the entity, and scene-material may restore a mesh. So the sync also runs on `Changed<MeshMaterial3d<StandardMaterial>>` for a target: a handle that is not the entity's copy is the target's new original, copied (or its existing copy reused) and swapped back. Our own swap inserts the copy, which the check skips, so it does not loop. A target whose `MeshMaterial3d` is removed (`remove_material`, a script material swapped in) is dropped from the targets.
7. **Per-frame cost.** A copy edited is a `StandardMaterial` re-prepared by the renderer: its uniform data rewritten, no pipeline work. The mode changes only when alpha crosses 1, which re-specializes once. For agent-town, a handful of shapes (one copy each) and 10 roots times their distinct materials (Synty buildings share a few atlas materials, so tens, not hundreds) re-prepare per frame for 2 s. The cost that lasts is batching: while an entity holds copies its meshes no longer share a material with others, so they draw in their own batches. It ends when `MaterialAlpha` is removed or the entity despawns. An entity at alpha 1 still holds copies; docs say to remove the component when not fading.
8. **The seam with scene-material** (agreed with build-scene-material, 2026-10-23). `alpha.rs` calls `scene_entities`. scene-material does all its swaps and restores in `SceneMaterialSet`, a public `SystemSet` in `PostUpdate`; its `WorldInstanceReady` observer only records the root. `alpha.rs` does the same: its observer records the root, and its sync is a `PostUpdate` system `.after(SceneMaterialSet)`, so scene-material's commands are applied before it reads. A mesh with a `ScriptMaterial3d` has no `StandardMaterial` and is skipped. The one overlap is ours to own: scene-material may swap a mesh that holds our copy and record the copy as its original in `SceneMaterialTargets` (public). On `MaterialAlpha` removal, `alpha.rs` rewrites any copy in that root's `SceneMaterialTargets` back to its original. When scene-material restores while `MaterialAlpha` is on, the mesh gets our copy back, which is right.
9. **Hot reload.** A glTF saved again: Bevy replaces its labelled materials in place and respawns or re-readies the instance. On `AssetEvent::Modified` of an original, its copy is rebuilt from the new value; on `WorldInstanceReady`, stale targets are dropped and the walk runs again. A TS save keeps the entity and re-applies `MaterialAlpha` as a component field, so `Changed` runs the sync; a changed `<material>` gives a new handle, which decision 6 copies.
10. **Protocol.** Untouched: no editor method or event changes. `MaterialAlpha` shows in the inspector as any reflected component.

## Risks

- Blended meshes sort per mesh, so overlapping parts of one building may draw in the wrong order mid-fade. Accepted for a 2 s fade; premultiplied or dithered fades are follow-ups.
- Bevy casts no shadow from `Blend` meshes, so a shadow vanishes as the fade starts.
- A system that gives a target its own material while faded keeps it (decision 6 treats it as the new original); on removal the target gets that material back. Accepted: the newest material wins, as it would with no fade.
